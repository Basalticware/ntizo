/admin/users/$userId

One person, and whether they run the platform

The provider detail page's skeleton, reused: back link, a "who this is" section of label/value pairs, a decision section whose buttons the server chooses, then a list. Nothing here is new chrome.

  • One column decides

    ntizo_user.user.role is what authorization reads on every request, so a change applies on the next request. better_auth.user.role is written in the same transaction only so the two stop disagreeing.

  • One guard keeps an admin

    Nobody changes their own role, so whoever makes a change is still an admin afterwards. The command re-checks that under a row lock, which closes the one gap: two admins removing each other at the same instant.

  • Confirm, then write

    Granting full platform access is heavier than approving a business, so both directions go through an in-app dialog, never a browser alert.

Pendente

Header: the name as the page title and the email as its subtitle, through the same usePageHeader the provider page uses. The back link returns to the list with its search and filter as they were.

Who this is: the profile photo where there is one, initials otherwise, exactly as the provider page falls back from a logo. Email and phone carry their verification state beside the value; "por verificar" is amber because it is worth noticing, not an error. The ID is monospaced because support quotes it.

Left out on purpose: bio, date of birth, gender, timezone. The list's projection already refuses them, and this screen answers the same question: who is this, what can they do, is anything wrong.

Espaços: the same word as the list's column, counted from the same provider_member rows, so the number in the list and the rows here always agree. Role uses the workspace's own words (Proprietário, Colaborador); the badge is the business's status. The whole row opens /admin/providers/$id; the name underlines on hover, as it does in the provider queue. Empty state: "Não pertence a nenhum espaço."

Dar acesso de administração a Ana Sitoe?

A partir do próximo pedido que fizer, a Ana passa a poder:

  • aprovar, recusar e suspender negócios
  • definir comissões
  • ver todos os utilizadores, reservas e pedidos de suporte
  • mudar o papel de outras pessoas, incluindo o seu

Fica registado na actividade, com o seu nome.

Neutral in gender: "Dar acesso de administração a Ana Sitoe", never "tornar administradora". The name is the display name, or the email when there is none.

"incluindo o seu": the one line that makes an admin pause. A new admin can take this admin's role away; that is true and it belongs in the sentence that grants it.

While saving: both buttons disabled, a spinner in "Dar acesso". On success the dialog closes, the detail refetches, the Papel pair reads "Administrador", and the section offers "Retirar admin".

D · "Retirar acesso", refused mid-flight

Retirar o acesso de administração a Carlos Mondlane?

O Carlos deixa de ver a administração a partir do próximo pedido. Os espaços a que pertence não mudam.

Já não tem acesso de administração: outro administrador retirou-o entretanto. Nada foi alterado.

B: outline, not red. Removing access is reversible with one more click; the confirm button inside the dialog is the red one ("Retirar acesso").

C replaces the button with a sentence, the way the provider page says "no actions" for an archived business. The lock icon says "not available" without looking like an error. There is no "only admin left" state: the person reading this page is an admin and is not the target, so the target is never the last one.

D is the race the row lock exists for: two admins removing each other at once. The first to commit wins; the second finds, under the lock, that it is no longer an admin and is refused with ADMIN_ONLY, so the platform can never be left with none. The dialog keeps its place, shows the reason, and its only action becomes "Fechar". The other codes, CANNOT_CHANGE_OWN_ROLE and USER_NOT_FOUND, get their own sentences plus a generic fallback.
